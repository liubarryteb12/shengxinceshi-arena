## 1. 总览

### 1.1 P1 定位

P1 是生信分析 agent 工作流。用户只描述需求，agent 负责实现、适配、注册、执行、记录、沉淀。

### 1.2 运行架构

> 所有代码运行在本地。  
> 工作空间在本地。  
> Agent 在本地。  
> Streamlit 在本地。  
> R / Python 环境在本地。  
> 默认本地执行，可选 GitHub Actions 后端。

```text
用户本地
  ├── 工作空间
  ├── Agent
  ├── Streamlit
  ├── R 环境
  ├── Python 环境
  └── 脚本执行（默认本地）
        ↓ 可选
GitHub Actions（公开仓库，无时间限制）
```

### 1.3 P1 完整流程

```text
P1 第 0 步：工作空间初始化与数据迁移
  ↓
P1 第 1 步：模块注册与发现
  ↓
P1 第 2 步：用户选模块与顺序（Streamlit）
  ↓
P1 第 3 步：依赖检查与顺序建议（agent）
  ↓
P1 第 4 步：流程草案与确认（agent + Streamlit）
  ↓
P1 第 5 步：执行引擎（本地 / GitHub Actions）
  ↓
P1 第 6 步：记录、质控、结果结构化
  ↓
P1 第 7 步：生成 P1 接口文件
  ↓
P2 / P4
```

### 1.4 核心原则

- 用户管方向和取舍，agent 管执行和记录。
- 一切皆文件，一切有描述，一切可追溯，一切可复现。
- 脚本不硬编码路径，不硬编码参数，一切从 JSON 读。
- 模块之间只通过缓存和结果描述文件对接。
- 单语言模块也走 steps，只是只有一个 step。
- Web 只产出草案，agent 不依赖 Web。
- 默认本地执行，云端是可选加速器。
- 云端只执行，记录在本地。
- **每条规则必须能构造 FAIL 用例，否则不立。**

### 1.5 Streamlit 的定位

Streamlit 只做两件事：

1. 第 2 步：让用户选模块、排初步顺序，产出 `user_draft.yaml`。
2. 第 4 步的确认界面：展示 agent 生成的正式草案，让用户确认。

第 3、4 步的逻辑归 agent，不在 Streamlit。

## 2. P1 第 0 步：工作空间初始化与数据迁移

### 2.1 核心规则

> 用户告诉 agent 原始数据地址后，agent 不直接分析。先问用户工作空间建在哪里，确认后展开工作空间，再把原始数据迁移到工作空间对应目录，校验通过后才开始分析。

### 2.2 流程

```text
用户启动 P1
  ↓
Agent 询问：工作空间建在哪里？
  ↓
用户指定本地路径
  ↓
Agent 检查路径是否可用
  ↓
Agent 展开工作空间目录结构
  ↓
Agent 询问：原始数据在哪里？
  ↓
用户提供原始数据地址、类型、补充信息
  ↓
Agent 检查原始数据是否可访问
  ↓
Agent 迁移原始数据到工作空间 inputs/
  ↓
Agent 校验迁移完整性
  ↓
Agent 写入迁移记录
  ↓
Agent 执行数据可用性分析
  ↓
进入 P1 正式分析流程
```

### 2.3 路径检查项

| 检查项 | 说明 | 失败动作 |
|---|---|---|
| 路径是否存在 | 父目录是否存在 | 询问是否创建 |
| 是否可写 | 当前用户是否有写权限 | 报错，要求换路径 |
| 空间是否足够 | 剩余空间是否满足预估 | 警告 |
| 是否为空 | 目录是否已有内容 | 询问是否覆盖/新建子目录 |
| 是否合法 | 路径是否含非法字符 | 报错 |

### 2.4 迁移方式

默认**复制**，原始数据保持只读。

| 方式 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 复制 | 原始数据不动，安全 | 占双倍空间 | 默认 |
| 移动 | 省空间 | 原始位置丢失，风险高 | 用户明确要求时 |

### 2.5 迁移目标目录

| 数据类型 | 目标目录 |
|---|---|
| 原始测序数据 | `inputs/raw/` |
| 样本表、分组表 | `inputs/metadata/` |
| 外部参考数据 | `inputs/external/` |
| 其他补充 | `inputs/metadata/` |

### 2.6 迁移校验

| 校验项 | 说明 | 失败动作 |
|---|---|---|
| 文件存在 | 源文件是否存在 | stop |
| 可读性 | 源文件是否可读 | stop |
| 空间足够 | 目标空间是否足够 | stop |
| checksum 一致 | 迁移前后是否一致 | stop |
| 文件数量一致 | 迁移前后数量是否一致 | stop |
| 文件大小一致 | 迁移前后大小是否一致 | warn |

## 3. P1 第 1 步：模块注册与发现

### 3.1 用户只描述功能，agent 全包实现与注册

用户不需要：模块 ID、分类、语言、输入输出格式、参数定义、脚本路径。

### 3.2 注册流程

```text
用户描述需求
  ↓
agent 理解需求
  ↓
agent 设计模块草案（module_design.yaml）
  ↓
用户确认设计
  ↓
agent 生成 module.yaml
  ↓
agent 生成脚本
  ↓
多模型复审
  ↓
复审通过
  ↓
agent 注册到 module_index.yaml
  ↓
agent 报告用户
```

## 5. P1 第 3 步：依赖检查与顺序建议

### 5.1 检查内容

| 检查项 | 说明 |
|---|---|
| 依赖是否满足 | 上游模块是否已选 |
| 依赖是否可用 | 上游模块是否可用 |
| 依赖是否循环 | 是否有循环依赖 |
| 输入是否可得 | 输入文件是否可得 |
| 输出是否匹配 | 上游输出能否匹配下游输入 |
| 版本是否兼容 | 模块版本是否兼容 |

### 5.2 检查结果类型

| 类型 | 说明 | 动作 |
|---|---|---|
| `pass` | 通过 | 继续 |
| `warning` | 警告 | 提示，可继续 |
| `error` | 错误 | 阻止，需修改 |
| `missing` | 缺依赖 | 建议补充 |
| `cycle` | 循环依赖 | 阻止，需修改 |

### 5.3 依赖检查报告

文件：`analysis/_index/dependency_check.yaml`

```yaml
check_id: dep_20260915_140000
timestamp: 2026-09-15T14:00:00+08:00
selected_modules:
  - quality_control
  - deseq2
  - enrichment

user_order:
  - quality_control
  - deseq2
  - enrichment

results:
  - module_id: deseq2
    status: pass
    message: 依赖 normalization 已满足
  - module_id: enrichment
    status: pass
    message: 依赖 deseq2 已满足

issues: []
suggestions:
  - 建议在 deseq2 前加入 normalization
```

### 5.4 顺序建议逻辑

| 依据 | 说明 |
|---|---|
| 依赖关系 | 上游必须先跑 |
| 数据流向 | 从原始数据到结果 |
| 模块特性 | 质控先于分析，分析先于可视化 |
| 用户目标 | 用户想回答什么问题 |
| 最佳实践 | 领域通用流程 |

### 5.5 建议结果类型

| 类型 | 说明 |
|---|---|
| `no_change` | 顺序合理，无需改 |
| `reorder` | 建议调整顺序 |
| `add` | 建议补充模块 |
| `remove` | 建议移除模块 |
| `replace` | 建议替换模块 |

### 5.6 用户拒绝后的处理

- 用户拒绝，agent 记录。
- 用户坚持，agent 执行。
- 执行报错，agent 诚实报告。
- 报告写入 `handoff.md` 和 `diff.md`。

## 7. P1 第 5 步：执行引擎

### 7.1 执行引擎总流程

```text
读 flow_confirmed.yaml
  ↓
读取执行后端配置
  ↓
校验输入是否就绪
  ↓
按步骤逐个执行
  ↓
每一步：
  ├── 准备输入
  ├── agent 生成脚本（draft）
  ├── 多模型复审
  ├── 复审通过？修改 → 再复审 → 超限报用户
  ├── 执行脚本（本地 / GitHub Actions）
  ├── 收集输出
  ├── 判断是否沉淀为模板
  ├── 写 manifest.yaml
  ├── 质控检查
  ├── 写 handoff / diff / checkpoint / next-tasklist
  └── 下一个 step
  ↓
全部完成
  ↓
生成 P1 接口文件
```

核心原则：

> 一次只跑一个模块，跑完写记录，再跑下一个。不并行，不跳步，不猜。

### 7.2 调度

调度只读 `flow_confirmed.yaml` 里的 `flow` 列表，按顺序执行。

每个步骤状态：

```text
pending → running → success
                  → failed
                  → skipped
                  → blocked
```

整个 run 状态：

```text
running → completed
        → partial
        → failed
        → aborted
```

运行记录：`analysis/_runs/run_{timestamp}/run.yaml`

```yaml
run_id: run_20260915_143000
status: running
current_step: 3
execution_backend: local
steps:
  - step: 1
    module_id: quality_control
    status: success
  - step: 2
    module_id: normalization
    status: success
  - step: 3
    module_id: deseq2
    status: running
  - step: 4
    module_id: enrichment
    status: pending
```

### 7.3 脚本生成

脚本不是"临时脚本"，而是**可生长的分析脚本**。

四个阶段：

```text
生成 → 复审 → 执行 → 沉淀
```

脚本目录：

```text
analysis/modules/{module_id}/
├── scripts/
│   ├── r/
│   │   ├── draft/
│   │   ├── run/
│   │   └── templates/
│   ├── python/
```

### 7.4 多模型复审

复审角色分工：

| 角色 | 审什么 | 不审什么 |
|---|---|---|
| 角色 A：代码逻辑审查 | 逻辑正确性、边界、异常 | 生信方法、规范 |
| 角色 B：生信专业审查 | 方法适用性、统计、参数 | 代码风格、规范 |
| 角色 C：代码规范审查 | 可读性、可复现、路径 | 逻辑、生信方法 |
| 角色 D：整体流程审查 | step 衔接、格式兼容 | 单脚本细节 |

复审流程：

```text
脚本生成
  ↓
角色 A 审 → 角色 B 审 → 角色 C 审
  ↓
汇总意见
  ↓
agent 修改
  ↓
角色 D 整体审
  ↓
复审通过
  ↓
执行
```

### 7.6 扩展机制

核心字段固定 + 扩展字段自由。

```json
{
  "schema_version": "1.0",
  "meta": {},
  "inputs": [],
  "outputs": [],
  "parameters": {},
  "environment": {},
  "log": {},
  "extensions": {},
  "custom": {}
}
```

| 字段 | 说明 |
|---|---|
| `schema_version` | JSON 格式版本 |
| `extensions` | 通用扩展，agent 认识结构但不解析内容 |
| `custom` | 模块私有扩展，agent 完全不解析 |

规则：

- 加扩展字段，schema_version 不变。
- 加核心字段，升小版本。
- 改核心字段，升大版本。
- 新增模块不用改执行引擎。
- 旧模块不受影响。

### 7.8 缓存传递

上游模块跑完写 `manifest.yaml`，下游模块读上游 manifest，从 manifest 里找输出路径。

缓存过期判断：

| 情况 | 动作 |
|---|---|
| 上游未跑 | 阻塞，先跑上游 |
| 上游跑了，输入未变 | 直接用缓存 |
| 上游跑了，输入变了 | 重跑上游 |
| 上游跑了，参数变了 | 重跑上游 |
| 上游跑了，版本变了 | 重跑上游 |
| 上游跑了，checksum 变了 | 重跑上游 |

缓存索引：`analysis/_index/cache_index.yaml`

### 7.9 错误处理

错误类型：

| 类型 | 例子 | 处理 |
|---|---|---|
| 路径错误 | 文件找不到 | agent 自动修 |
| 格式错误 | CSV 列名不对 | agent 自动修 |
| 参数错误 | 阈值超范围 | agent 自动修或问用户 |
| 依赖缺失 | 包没装 | agent 自动装 |
| 版本冲突 | 包版本不兼容 | agent 调整 |
| 语法错误 | 脚本报错 | agent 自动修 |
| 数据问题 | 样本量不足 | 问用户 |
| 逻辑错误 | 结果不对 | 问用户 |
| 环境问题 | 内存不足 | 报用户 |

重试上限：

| 错误类型 | 最大重试 |
|---|---|
| 路径/格式/语法 | 3 次 |
| 依赖/版本 | 3 次 |
| 数据问题 | 0 次，直接问用户 |
| 逻辑错误 | 1 次，然后问用户 |
| 环境问题 | 0 次，直接报用户 |

### 7.11 记录四件套

#### handoff.md

给人和 P2 看的交接单。回答 7 个问题：

1. 这一步是什么
2. 这一步做了什么
3. 输入是什么
4. 输出是什么
5. 结果怎么样
6. 能不能用
7. 下一步建议

#### diff.md

和上次运行对比：参数变化、输入变化、输出变化、结论。

#### checkpoint.yaml

恢复锚点。每步成功后写，不可变。

#### next_tasklist.md

推荐下一步、可选下一步、阻塞项、优先级。

### 7.12 质量控制

通用检查项：

| 检查项 | 说明 | 失败动作 |
|---|---|---|
| `input_completeness` | 输入文件是否齐全 | stop |
| `input_format` | 输入格式是否正确 | stop |
| `input_checksum` | 输入 checksum 是否匹配 | warn |
| `sample_size` | 样本量是否满足最小要求 | stop |
| `missing_value` | 缺失值比例是否超标 | warn |
| `outlier_detection` | 是否有异常样本 | warn |
| `batch_effect` | 是否有批次效应 | warn |
| `normalization` | 是否已标准化 | stop |
| `parameter_validity` | 参数是否合法 | stop |
| `output_completeness` | 输出是否齐全 | stop |
| `output_format` | 输出格式是否正确 | stop |
| `reproducibility` | 随机种子是否固定 | warn |

### 7.13 脚本沉淀

四个条件：跑通、审过、效果好、通用性强。

### 7.14 中断和恢复

中断类型：

| 类型 | 说明 |
|---|---|
| 用户中断 | 用户主动点停止 |
| 系统中断 | 断电、重启、进程被杀 |
| 超时中断 | 单步超时、总超时 |
| 错误中断 | 模块失败且无法自动修 |
| 资源中断 | 内存不足、磁盘满 |
| 依赖中断 | 上游失败，下游阻塞 |

恢复方式：

| 方式 | 说明 |
|---|---|
| 继续 | 从断点继续 |
| 重跑当前 | 重跑当前 step |
| 回退一步 | 从上一步重跑 |
| 从头重跑 | 全部重跑 |

### 7.15 编号规则 partn-n-output

格式：`part{P}-{M}-output`

示例：

```text

```

规则：

- 编号按流程执行顺序分配。
- 一个功能单元一个编号。
- 编号一旦分配，不回收、不复用。
- 最终结果带标签，中间量不带标签。

### 10.2 对比

| 项 | local | github_actions |
|---|---|---|
| 默认 | 是 | 否 |
| 运行位置 | 本地 | GitHub Actions |
| 数据 | 本地 | 需上传 |

| 时间限制 | 无 | 单 job 6 小时 |
| 分钟数 | 不涉及 | 公开仓库无限制 |
| 结果 | 本地直接写 | 需回传 |
| 适合 | 调试、短任务 | 长任务、批量 |

### 10.3 规则

1. 默认本地执行。
2. GitHub Actions 是可选后端。
3. 通过 `workspace.yaml` 切换。
4. 先本地调试，跑通再上传。
5. 云端只执行，记录在本地。
6. 数据上传视大小选方案。
7. 结果回传视大小选方案。
8. 环境用 requirements / renv / Docker。
9. 中断靠取消 workflow。
10. 口子留在配置、Streamlit、执行引擎、目录结构。

## 11. 图片产出规格前置

### 11.1 核心规则

> P1 的图表模块在生成图片时，就按 P3 的出图安全规格产出，不等 P3 再转。

### 11.2 产出规格

| P1 图表类型 | 产出规格 |
|---|---|
| 分析图（火山图、热图、PCA、生存曲线等） | 矢量 PDF + SVG + PNG + TIFF + JPG 五格式；宽度按 85/180 mm |
| 显微图 / 电镜图 | TIFF（LZW）600 dpi，RGB |
| WB / 凝胶 | TIFF（LZW）灰度 600 dpi |
| 组合图 | TIFF（LZW）500–600 dpi |

### 11.3 出图时遵守

- 字体 Arial / Helvetica，7–8 pt。
- 线宽 0.25–1 pt。
- 颜色色盲友好，避免红绿对比。
- 图内无图题、无图注、无网格。
- 单文件 ≤10 MB。
- 命名 `Figure_N` 或 `{NN}_{step}_{desc}`，全链路统一。

### 11.4 图表编号与引用一致

P1 输出的图表编号必须与 P2/P3 的正文引用一致，命名格式在 P1 就定死，P2/P3 不改。

## 12. 消融实验设计

### 12.1 核心规则

> 每个守卫（质检规则、一致性检查、复审规则）必须能通过变异测试：现场注入违规，当场验证能抓到。**抓不到 = 空规，不得计入"通过"。**

### 12.2 P1 消融用例

| # | 判据 | 注入方式 | 期望触发 |
|---|---|---|---|
| Q1 | 图表五格式齐全 | 删 svg | 格式检查 FAIL |
| Q2 | 命名与 P2 一致 | 改命名 | 命名检查 FAIL |
| Q3 | 显微图 TIFF 600dpi | 降 300 | dpi 检查 FAIL |
| Q4 | 凝胶/印迹 TIFF 灰度 600dpi | 改 RGB | 格式检查 FAIL |
| Q5 | 分析图矢量优先 | 改位图 | 类型检查 FAIL |
| Q6 | 图表编号与 P1 接口一致 | 改编号 | 一致性检查 FAIL |

### 12.3 消融记录

文件：`analysis/_runs/mutation_results.json`

```json
{
  "n_pass": 0,
  "total": 0,
  "coverage": "0%",
  "cases": [
    {
      "case_id": "P1-Q1",
      "check_id": "P1.Q1.format",
      "anchor": "figure.svg",
      "injected": "removed",
      "expect_fail": true,
      "caught": false,
      "verdict": "空规"
    }
  ]
}
```

### 12.4 消融通过标准

| 标准 | 说明 |
|---|---|
| 每个 A 档判据至少 1 个变异用例 | 骨架比例 100% |
| 每个 A 档判据变异用例能抓到 | 抓不到 = 空规 |
| 每个 A 档判据**先 FAIL 后 PASS** | 唯一有效证据 |
| 休眠比例 ≤ 20% | 超过判"判据膨胀" |
| GLOBAL 占比 ≤ 10% | 超过判"归因稀释" |

## 17. Agent 权限边界总览

### 能自动做的

- 执行迁移。
- 校验迁移完整性。
- 写迁移日志。
- 执行数据可用性分析。
- 扫描模块。
- 生成模块索引。
- 解析自然语言选模块。
- 检查依赖。
- 生成顺序建议。
- 生成流程草案。
- 分配编号。
- 生成脚本。
- 多模型复审。
- 执行模块。
- 收集输出。
- 写记录。
- 质控。
- 错误重试（有限次）。
- 缓存管理。
- 脚本沉淀。
- 中断检测。
- 恢复检查。
- 切换执行后端。
- 生成图片（按 P3 规格）。
- 运行变异测试。

### 不能自动做的

- 不能擅自决定工作空间路径。
- 不能擅自移动原始数据。
- 不能覆盖已有工作空间。
- 不能跳过迁移校验。
- 不能修改原始数据。
- 不能替用户选模块。
- 不能替用户定顺序。

- 不能改模块定义。
- 不能编造结果。

- 不能跳过质控。
- 不能改已分配的编号。
- 不能改 run.yaml 历史。

## 18. 规则总览

### 18.1 总体规则

1. 用户管方向和取舍，agent 管执行和记录。
2. 一切皆文件，一切有描述，一切可追溯，一切可复现。
3. 模块描述定义"能做什么"，结果描述定义"做了什么"。
4. 缓存目录定义"东西在哪"，编号规则定义"怎么引用"。
5. 记录文件定义"怎么复盘"。
6. 单语言模块也走 steps，只是只有一个 step。
7. Web 只产出草案，agent 不依赖 Web。
8. 用户只说功能，agent 全包实现与注册。
9. 默认本地执行，云端是可选加速器。
10. 云端只执行，记录在本地。
11. **每条规则必须能构造 FAIL 用例，否则不立。**

### 18.2 模块规则

1. 模块 ID 唯一。
2. 模块按 category 分组。
3. 模块语言在 module.yaml 里声明。
4. 模块用 steps 描述多步流程。
5. 模块之间只通过缓存和结果描述文件对接。
6. 脚本按语言分 `r/` 和 `python/`。
7. 模块注册由 agent 自动完成。

### 18.3 脚本规则

1. 脚本不硬编码路径。
2. 参数从 JSON 读。
3. 输入输出路径从 JSON 读。
4. 随机种子固定。
5. 写日志。
6. 写中间结果。
7. 脚本生成后必须复审。
8. 跑通、审过、效果好、通用性强才沉淀。
9. 沉淀按语言分别存。
10. 复用模板也要复审。

### 18.4 复审规则

1. 一个角色一个 prompt。
2. 每个 prompt 只审自己那块。
3. 输出格式统一为 YAML。
4. 严重程度分 major/minor/info。
5. 必须给行号和修改建议。
6. 必须给 status 和 summary。
7. 多模型交叉，减少偏差。
8. 复审不通过走错误处理。
9. 复审通过才沉淀。
10. 用户可强制通过。

### 18.5 执行规则

1. 一次只跑一个模块。
2. 不并行，不跳步，不猜。
3. 上游完成才跑下游。
4. 上游失败，下游阻塞。
5. 模块失败有限重试。
6. 重试超上限报用户。
7. 模块成功后写 manifest 和四件套。
8. 模块失败后写 error_log。
9. 缓存不因中断删除。
10. 恢复前必须检查。

### 18.6 编号规则

1. 格式：`part{P}-{M}-output`。
2. 序号按流程执行顺序分配。
3. 一个功能单元一个编号。
4. 编号一旦分配，不回收、不复用。
5. 最终结果带标签，中间量不带标签。
6. 编号由 agent 自动分配，用户可查、可改。

### 18.7 记录规则

1. 每个模块成功后必写 manifest。
2. 每个模块成功后必写 handoff。
3. 每个模块成功后必写 diff。
4. 每个模块成功后必写 checkpoint。
5. 每个模块成功后必写 next_tasklist。
6. handoff 回答 7 个问题。
7. handoff 不写脚本细节，不写代码。
8. handoff 必须写"能不能用"和"下一步建议"。
9. 失败也写，写失败版。
10. 恢复后追加，不覆盖。

### 18.8 中断恢复规则

1. 中断有类型。
2. 中断等安全点。
3. 每步成功后写 checkpoint。
4. checkpoint 不可变。
5. 恢复读最新 checkpoint。
6. 恢复前必须检查。
7. 恢复方式由用户决定。
8. 系统中断靠 checkpoint 恢复。
9. 缓存不因中断删除。
10. 恢复记录写入 resume_log。

### 18.9 接口规则

1. P1 完成后自动生成接口文件。
2. P2 只读接口文件，不直接读模块脚本。
3. P4 只读接口文件，不直接读模块脚本。
4. 接口文件由 agent 自动维护。
5. P2 只读 handoff 和 evidence。
6. P4 只读 p1_to_p4_quality。

### 18.10 扩展规则

1. 核心字段不动，扩展字段随便加。
2. agent 不认识扩展字段，但会原样传给脚本。
3. 加扩展字段，schema_version 不变。
4. 加核心字段，升小版本。
5. 改核心字段，升大版本。
6. 新增模块不用改执行引擎。
7. 旧模块不受影响。
8. 扩展字段默认可选。

### 18.11 执行后端规则

1. 默认本地执行。
2. GitHub Actions 是可选后端。
3. 通过 `workspace.yaml` 切换。
4. 先本地调试，跑通再上传。
5. 云端只执行，记录在本地。
6. 数据上传视大小选方案。
7. 结果回传视大小选方案。
8. 环境用 requirements / renv / Docker。
9. 中断靠取消 workflow。
10. 口子留在配置、Streamlit、执行引擎、目录结构。

### 18.12 图片规则

1. P1 图表按 P3 出图规格前置产出。
2. 五格式齐全（pdf/png/tiff/jpg/svg）。
3. 显微图 TIFF 600 dpi。
4. 凝胶/印迹 TIFF 灰度 600 dpi。
5. 分析图矢量优先。
6. 命名与 P2/P3 全链路统一。
7. 图表编号与 P1 接口一致。

### 18.13 消融规则

1. 每个 A 档判据至少 1 个变异用例。
2. 变异用例必须能抓到。
3. 先 FAIL 后 PASS 是唯一有效证据。
4. 抓不到 = 空规，不得计入"通过"。
5. 休眠比例 ≤ 20%。
6. GLOBAL 占比 ≤ 10%。
7. 锚点必须唯一。
